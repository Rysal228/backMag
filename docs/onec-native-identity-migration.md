# Переход от UUID Django к штатному идентификатору справочника 1С

## Решение

- **Целевой идентификатор пользователя:** уникальный идентификатор ссылки `СправочникСсылка.ПользователиПриложения`, доступный как `Строка(Ссылка.УникальныйИдентификатор())`.
- **Текущий идентификатор:** поле `CustomUser.id` в Django, перенесённое в реквизит `ИдентификаторВнешний` справочника 1С как `externalId`.
- **Промежуточный ответ 1С:** одновременно `externalId` (старый UUID) и `onecId` (родной идентификатор 1С). Ничего не перезаписываем.
- **Внешний контракт Angular пока прежний:** в `user.id` и `mechanics[].id` остаются Django UUID. **Не подменять id в ответе на onecId до миграции связей заказов и JWT**.

Штатная ссылка 1С — объектный идентификатор 1С, а не произвольная дополнительная строка. На стороне Django после полного переноса нужен лишь сериализуемый UUID ссылки, чтобы обращаться к 1С; дублировать пользовательскую бизнес-сущность в Django не требуется.

## Уже подтверждённые зависимости текущего приложения

- JWT: SimpleJWT `RefreshToken.for_user(user)` формирует `user_id` из `CustomUser.pk`; `RoleJWTAuthentication` обращается к Django. Refresh/выбор роли/MAX проверяют локальную строку.
- `cars.Car.owner` и `cars.CarOwnership.owner` — ForeignKey на `CustomUser`.
- `orders.Order.customer` — ForeignKey на `CustomUser`, `orders.Order.mechanics` — ManyToMany на `CustomUser`.
- `orders.OrderSerializer.mechanics` принимает список первичных ключей из Django, которые Angular получает через `GET /api/v1/users/?role=mechanic`.
- Строковые параметры клиента `/api/v1/users/profile/` и механики уже работают через 1С, но текущая сессия Django ещё использует Django PK и телефон.
- MAX имеет локальную привязку `messenger_user_id` и отдельные данные подтверждения; менять только после согласования с владельцем проекта.

## Этап 1 — проверка соответствий (сделано в GitHub, развёртывается отдельно)

В рабочей 1С, после резервного копирования, обновить только
`Функция ПредставлениеПользователя(Ссылка)` в HTTP-модуле `ServiceCarAPI`
строкой:

```bsl
Данные.Вставить("onecId", Строка(Ссылка.УникальныйИдентификатор()));
```

Рядом с `externalId`. Проверить синтаксис и обновить конфигурацию.
Ни структура БД 1С, ни Django, ни Angular при этом не меняются.
Не заменять весь живой HTTP-модуль без сравнения с его текущими изменениями.

После развёртывания Django выполнить:

```bash
docker compose exec backend python manage.py audit_onec_user_ids --phone 79135552525
docker compose exec backend python manage.py audit_onec_user_ids --all
```

Команда читает `CustomUser.id/phone` и `GET /user/{phone}` из 1С, проверяет соответствие UUID, телефона, уникальность nativeId и выводит пары. **Не пишет данные**, при любой ошибке завершится с ненулевым кодом. Выборка `--all` проверяет только пользователей, присутствующих в Django, и **не доказывает отсутствие дополнительных пользователей** непосредственно в 1С.

## Этап 2 — сохранить соответствие старого/нового ID

Сверить результаты и сохранить проверенную карту `legacy UUID -> onecId` в отдельном защищённом файле миграции (не в открытом GitHub). Не создавать второй живой справочник пользователей на стороне Django.

Если какой-то локальный пользователь не найден в 1С, UUID не совпадает, обнаружен повтор `onecId` или неверный телефон — остановить переход и разобраться.

## Этап 3 — подготовить связи автомобилей и заказов

Сначала добавить новые nullable UUID-колонки для владельца, истории владения, заказчика и отдельных связей `Order.mechanics`, **не удаляя** существующие ForeignKey и ManyToMany. Источник значений — проверенная карта соответствий.

Проверить заполнение **каждой** старой связи, число машин, заказов и назначений, отсутствие orphan-ссылок. Только после подтверждения переключить чтение/создание/фильтры и потом удалить старые ссылки. При переносе домена автомобилей/заказов в 1С эти же ссылки станут ссылками на пользователя 1С; здесь лишь снимаем техническую зависимость Django.

## Этап 4 — аутентификация и переход токенов

Новые JWT должны идентифицировать пользователя родным ID 1С, а Django должен получать текущее состояние/роли из 1С без локального `CustomUser`. Требуется новый способ определить учётную запись по идентификатору (не только по телефону) и переработать SimpleJWT authentication/refresh/token selection. Действующие токены используют старый UUID: предусмотреть совместимость или контролируемое завершение старых сессий.

Регистрация и пароль требуют отдельного решения по хранилищу паролей; MAX — **отдельного обсуждения до изменений**.

## Этап 5 — очистка

Только после фактической миграции связей, JWT, регистрации и MAX удалить `CustomUser`, локальные роли и `ИдентификаторВнешний` из 1С. Не делать это раньше. Закрепить нативный ID 1С в публичном API и обновить типы/состояние Angular.

## Текущая граница

Эта стадия **не меняет** формат JWT, профиля Angular, списка специалистов, заказов, регистрацию, MAX или связи в PostgreSQL. Она лишь позволяет получить родной ID 1С и проверить старые соответствия до изменения живых данных.
