# MAX: уведомления клиенту об изменениях статуса заказа

## Как работает

Отдельный **серверный процесс Django** раз в минуту получает из 1С
список заказов от имени **реального менеджера 1С**, а также
сопоставление автомобиль → владелец из 1С. Сравнение с сохранённым
снимком в PostgreSQL позволяет обнаруживать изменения, выполненные
как через Angular/Django, так и **непосредственно в форме 1С**.

- На первом запуске создаются **только исходные снимки**. Старым заказам
  сообщения не рассылаются.
- Изменение `СтатусЗаказа` / `СтатусРабот` добавляет **одну** запись
  в очередь, даже если обе колонки изменились одновременно.
- Отправка: существующий `MaxBotClient`, **тот же бот**, что доставляет
  коды входа. MAX ID получаем каждый раз по native UUID владельца из 1С.
- Если клиент не привязал MAX, неактивен или автомобиль сменил владельца,
  отправка пропускается. Чужой пользователь MAX ID не может быть задан в запросе.
- В сообщении только номер заказа, модель и новые статусы, по желанию
  ссылка на сайт. Нет номера телефона, VIN, цены и данных исполнителей.
- Уведомления о **платеже** не создаются: текущий ручной `paid` не равен
  подтверждённому эквайринговому платежу.
- 5 попыток с экспоненциальной задержкой при сетевой ошибке; журнал
  доступен только для просмотра в Django Admin.

## Установка и запуск

Добавить в окружение контейнера Django (не в Git):

```env
MAX_ORDER_NOTIFICATIONS_ENABLED=1
MAX_ORDER_NOTIFICATIONS_MANAGER_ID=<uuid реально существующего менеджера 1С>
MAX_ORDER_NOTIFICATIONS_PUBLIC_URL=https://www.cherser-car.site
```

Последний URL необязателен, но если установлен, допустим только HTTPS.
Сохраняйте `MAX_BOT_TOKEN` как секрет: используется существующая настройка.
В 1С никаких новых метаданных и прав доступа создавать не требуется.

```bash
cd autoservice
python manage.py migrate
python manage.py check
python manage.py test orders.tests.test_max_notifications
# Первый проход создаст базовые состояния без отправки старых событий
python manage.py poll_order_notifications --observe-only
# Далее проверка вручную после изменения статуса в 1С:
python manage.py poll_order_notifications
```

Для регулярных уведомлений планировщик НА СЕРВЕРЕ должен запускать команду
раз в минуту. Например, в cron хоста (уточните имя сервиса через
`docker compose config --services`):

```cron
* * * * * cd /opt/service-car && /usr/bin/docker compose exec -T backend python manage.py poll_order_notifications >> /var/log/servicecar-max-notifications.log 2>&1
```

Используйте реальное имя сервиса вместо `backend`. Одновременно
несколько копий задачи **не запускать**. Чтобы временно остановить доставку,
установить `MAX_ORDER_NOTIFICATIONS_ENABLED=0` и перезапустить контейнер.

## Проверка

1. Создать тестового владельца с подтверждённым MAX ID, автомобиль и заказ.
2. Запустить `--observe-only` и убедиться, что сообщений нет.
3. Изменить в форме **1С:Предприятие** статус заказа или работ и сохранить.
4. Запустить обычную команду. В MAX должно прийти одно сообщение с номером,
   автомобилем, статусом и ссылкой на заказ (если указан публичный URL).
5. Повторить без изменения статуса: второе сообщение не должно прийти.
6. Привести MAX API к временной недоступности: задача сохранит запись
   и попробует доставить её позднее.
7. Проверить клиента без привязки MAX и механика: информация о клиенте им
   не раскрывается и сообщения не отправляются сторонним получателям.

## Ограничения первого этапа

**Это опрос, а не outbox событий в самой 1С.** Если несколько изменений
одного заказа произошли между двумя запусками (например, за 60 секунд),
будет обнаружен только последний набор статусов. Чтобы доставлять *каждый*
переход без потерь, потребуется отдельный журнал изменений в 1С и его
подтверждаемая выгрузка. При таймауте после успешной отправки MAX возможна
повторная отправка (нет подтверждённой exactly-once доставки).

Для списка всех заказов используются существующие защищённые внутренние
HTTP-интерфейсы 1С; они по-прежнему должны быть **недоступны из интернета**.
`actorId/actorRole` сами по себе не являются аутентификацией. UUID менеджера
задаётся только на сервере, не передаётся с браузера.

Не размещайте cron в каждом Gunicorn-процессе: это отдельная задача.
