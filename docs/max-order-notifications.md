# MAX уведомления о статусах через служебный API 1С

Продолжение уже слитого PR #74. Опрос больше не зависит от пользователя,
UUID менеджера, его роли или открытой сессии. `MAX_ORDER_NOTIFICATIONS_MANAGER_ID`
удалён из настроек и не используется, даже если остался в окружении.

## Как работает

Раз в минуту планировщик запускает `poll_order_notifications`:

1. Django читает `GET /ServiceCar/hs/api/notifications/orders`.
2. Передаёт общий секрет в заголовке `X-ServiceCar-Notifications-Key`.
3. 1С сверяет его с записью `main` регистра `НастройкиСервисаУведомлений`.
4. Django сравнивает статусы с `OrderNotificationSnapshot` и создаёт записи
   `OrderNotificationDelivery`, как в #74.
5. Перед отправкой читает `GET /notifications/orders/{id}/recipient` с тем же
   служебным ключом. 1С проверяет существование заказа, актуальное соответствие
   клиента владельцу автомобиля, активность пользователя и MAX-привязку.
6. Только при совпадении UUID заказа, автомобиля и владельца с очередью
   сообщение отправляется через существующий MAX-бот.

Это авторизация приложения: ключ не является паролем человека, JWT, UUID или
учётной записью пользователя 1С. Он разрешает только два новых GET-метода.
Публичные операции пользователей, машин и заказов продолжают работать как раньше.
Endpoint не опубликован через Django для браузера.

Снимки, ревизии и очередь из миграции `0033` сохраняются. Новая миграция Django
не нужна. Обновление не создаёт повторный baseline существующих записей.
Удалённый заказ, изменившийся владелец или недействующая MAX-привязка приводят
к `skipped`; ошибка сервиса приводит к повторной попытке. Без ключа команда
останавливается до опроса и отправки, без перехода на старую схему с менеджером.

## Порядок обновления после PR 74

1. Если задача уже запущена — временно отключить её строку cron. Не очищать
   снимки и очередь, не запускать несколько экземпляров одновременно.
2. Сначала обновить **1С**: загрузить новые метаданные регистра, оба URL-шаблона
   и модуль `ServiceCarAPI`. Проверить конфигурацию F7, обновить конфигурацию БД
   и HTTP-публикацию. Перенос только BSL без XML недостаточен.
3. Создать случайный ключ локально на сервере (не отправлять в чат и Git):

   ```bash
   docker exec service-car-backend python -c 'import secrets; print(secrets.token_urlsafe(48))'
   ```

4. В 1С:Предприятии открыть **Функции для технического специалиста → Регистры
   сведений → Настройки сервиса уведомлений**. Создать одну запись:

   | Поле | Значение |
   | --- | --- |
   | Ключ | `main` |
   | Ключ доступа | Сгенерированное значение целиком |

   Поле ключа маскируется; история изменений и полнотекстовый поиск отключены.
   Это не замена правам ИБ: чтение/изменение регистра доступно только доверенному
   оператору и серверному контексту публикации. При отсутствии настроек или прав
   на чтение служебные методы возвращают 401, а не открывают доступ.

5. В окружение backend добавить то же значение, сохранить существующий токен бота:

   ```env
   MAX_ORDER_NOTIFICATIONS_ENABLED=1
   ONEC_NOTIFICATIONS_SERVICE_KEY=СКОПИРОВАННЫЙ_КЛЮЧ
   MAX_ORDER_NOTIFICATIONS_PUBLIC_URL=https://www.cherser-car.site
   ```

   `ONEC_NOTIFICATIONS_SERVICE_KEY`: от 32 до 128 символов `A-Z a-z 0-9 _ -`,
   чувствителен к регистру. UUID менеджера больше не нужен. URL сайта необязателен.
   Пустого или встроенного ключа по умолчанию нет.

6. Обновить исходники backend поверх #74, пересобрать и **пересоздать** контейнер,
   чтобы применилось новое окружение. Один `docker restart` не переносит новые
   переменные из Compose. Вызвать:

   ```bash
   docker exec service-car-backend python manage.py migrate
   docker exec service-car-backend python manage.py check
   docker exec service-car-backend python manage.py poll_order_notifications --observe-only
   ```

   Если задача раньше работала, `--observe-only` также обновляет старые снимки
   и создаёт очередь изменений, но не отправляет её. Это не dry run и не сброс
   baseline. На первом запуске без снимков только запоминаются исходные статусы.

7. Изменить статус тестового заказа в **клиенте 1С**, сохранить документ и вызвать:

   ```bash
   docker exec service-car-backend python manage.py poll_order_notifications
   ```

   Проверить сообщение в MAX и журнал Django Admin. Повтор без изменения не
   должен создавать ещё одно уведомление.
8. Вернуть запуск раз в минуту. Для известного имени контейнера:

   ```cron
   * * * * * /usr/bin/flock -n /run/lock/servicecar-max-notifications.lock /usr/bin/docker exec service-car-backend python manage.py poll_order_notifications >> /var/log/servicecar-max-notifications.log 2>&1
   ```

   Если контейнер называется иначе, заменить имя. Планировщик запускается на
   хосте, не в каждом процессе Django. Блокировка не даёт копиям cron пересекаться.

## Адрес и транспорт

Служебный клиент использует `ONEC_BASE_URL` и `ONEC_ORDERS_PATH` существующей
интеграции, по умолчанию `http://host.docker.internal:8081/ServiceCar/hs/api`.
Для этого точного внутреннего адреса сохранён совместимый HTTP-режим. Ключ в
нём передаётся без шифрования: канал должен оставаться только в доверенной сети
между Django и 1С. Для другого адреса требуется HTTPS с проверкой сертификата.
1С не должна быть доступна из интернета; ключ не передавать в URL или браузер.
Перенаправления отключены. Существующие пользовательские API не защищаются этим
новым ключом автоматически: их сетевые ограничения остаются обязательными.

При ротации приостановить задачу, заменить ключ в записи 1С и окружении backend,
пересоздать контейнер и вернуть задачу. Не включать запись HTTP-заголовка с ключом
в логи публикации или proxy.

## Проверки

```bash
cd autoservice
python manage.py test orders.tests.test_max_notifications orders.tests.test_onec_notifications_gateway
```

Unit-тесты используют заглушки 1С и MAX. Проверяются служебный заголовок,
отсутствие actor/manager, отказ на некорректном ключе/JSON/UUID/redirect,
проверка получателя, сохранение ревизий и отправка старой очереди #74.
Они не заменяют F7 и запросы к установленной 1С. В репозитории 1С есть
`tools/smoke_notification_service.py` для read-only проверки обоих методов,
неправильного/отсутствующего ключа и попытки подмены actor. При проверке
регистра нужно отдельно подтвердить отказ с пустым ключом в БД.

## Неизменившиеся ограничения

Это периодический опрос текущих состояний. Промежуточные переходы между опросами
могут быть потеряны. Если новый заказ изменился до своего первого наблюдения,
будет сохранено его текущее исходное состояние без ретроспективной рассылки.
При изменении обоих статусов формируется одно сообщение. Статус оплаты не
отслеживается. Клиенты без действующей MAX-привязки не получают сообщения.
Сохраняются пять попыток с увеличивающейся паузой и ограничение одного сообщения
владельцу за запуск. Таймаут после фактической отправки MAX может дать дубль.
