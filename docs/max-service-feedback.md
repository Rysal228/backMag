# Оценки обслуживания после закрытия/отмены заказа через MAX

## Сценарий

- Только новые переходы статусов **`closed`** («автомобиль выдан»)
  и **`cancelled`** («заказ отменён») в 1С запускают запрос оценки.
  `completed` означает «ремонт готов», **не** фактическую выдачу, поэтому
  оценки не запрашивает. `refused` — статус работ, а не терминальный статус заказа.
- Запрос оценки отправляется владельцу заказа через действующую привязку MAX в 1С.
  Текущий владелец проверяется при отправке и повторно при каждом ответе.
  Номера телефонов и MAX user ID не сохраняются в PostgreSQL.
- Клиент нажимает одну из кнопок 1–5; оценка сразу и однократно сохраняется.
  Для низких оценок бот предлагает причины (для отменённого заказа — причины
  взаимодействия/отмены); для всех оценок — необязательный комментарий.
- Для комментария клиент нажимает кнопку «Написать комментарий» и отправляет
  обычное текстовое сообщение в течение 15 минут. Сессия привязана к
  криптографическому отпечатку MAX ID, необратимо вычисленному по секрету Django.
  Команды со знаком `/` бот не считает отзывом. Оценку можно поставить в течение 7 суток после
  отправки запроса; повторной рассылки нет.
- Django Admin → **Оценки и отзывы**: оценки, причины, комментарии,
  технический журнал отправок запросов и сводка по оценкам.

## Настройки в Django Admin

**Уведомления MAX → Настройки уведомлений MAX**:

| Поле | Значение |
| --- | --- |
| Оценки и отзывы через MAX | Включить или выключить автоматический запрос оценки |
| Запросить оценку через, минут | Одна задержка от 0 до 10080 минут для `closed` и `cancelled` (по умолчанию 30) |
| Низкая оценка: до | 1..N, по умолчанию 1..3 |
| Высокая оценка: от | M..5, по умолчанию 4..5 |

`N < M` обязательно; между диапазонами может существовать нейтральная оценка.
После изменения порогов Admin сразу пересчитывает категории старых отзывов
для фильтров и показателей, но уже сохранённые оценки не изменяются.
Задержка применяется **при постановке нового запроса оценки в очередь**;
ранее созданные запросы не пересчитывают `due_at`.

После первого включения worker формирует снимки всех наблюдаемых заказов:
**старые закрытые/отменённые заказы не рассылаются**. При повторном
включении накопленная за время паузы очередь пропускается и первоначальный
опрос после включения формирует новую базовую точку. Из-за отсутствия точного
времени терминального перехода в служебной ленте 1С событие, которое возникло
и успело стать терминальным до **первого** опроса, неотличимо от исторического
заказа и сознательно пропускается (приоритет — отсутствие массовой рассылки).
Для точного учёта таких переходов в будущем следует расширить сервис 1С
неизменяемой временной меткой закрытия/отмены или журналом событий.

## Развёртывание

1. Обновить backend, установить миграции: `python manage.py migrate`.
   1С и frontend обновлять **не требуется**: используется существующий
   `GET /notifications/orders` и `GET /notifications/orders/{uuid}/recipient`.
2. В окружении backend сохранить секрет `MAX_WEBHOOK_SECRET` **отдельно**
   от `MAX_BOT_TOKEN` и `ONEC_NOTIFICATIONS_SERVICE_KEY`. Рекомендуется
   случайный 32-байтовый секрет в URL-safe формате (`openssl rand -hex 32`).
   Пример Compose: `MAX_WEBHOOK_SECRET: ${MAX_WEBHOOK_SECRET:?required}`.
   Новых незащищённых токенов в Django Admin нет.
3. В MAX API проверить существующие Webhook-подписки `GET /subscriptions`:
   **не удалять существующие**, если другим обработчикам бота нужны события.
   Настроить `POST /subscriptions` с HTTPS URL
   `https://www.cherser-car.site/api/v1/feedback/max/webhook/`,
   секретом `MAX_WEBHOOK_SECRET` и типами событий `message_callback` и
   `message_created`. Если у бота уже есть подписка, сохранить её типы
   событий и маршрут или спроектировать единый диспетчер Webhook:
   отдельный endpoint для оценок **не должен** нарушать другие функции бота.
   MAX доставляет события webhook по HTTPS на порт 443; нужны корректные
   доверенный сертификат и маршрутизация `/api/v1/` через Nginx.
4. В Django Admin установить пороги и задержку, затем **включить** новый
   канал опросов. Сразу выполнить однократное наблюдение без отправки, чтобы
   создать исходные снимки исторических заказов:

   ```bash
   docker exec service-car-backend python manage.py poll_feedback_requests --observe-only
   ```

5. Добавить **третью cron-запись**, отдельную от статусов
   заказов и новостей:

   ```cron
   * * * * * /usr/bin/flock -n /run/lock/servicecar-max-feedback.lock /usr/bin/docker exec service-car-backend python manage.py poll_feedback_requests >> /var/log/servicecar-max-feedback.log 2>&1
   ```

   Для снижения пересечений по rate-limit с другими MAX-сообщениями можно
   разнести запуск задач по секундам. По умолчанию до 100 отправок за проход,
   не более одной за запуск на владельца, пять попыток с паузой при ошибке.

6. Вручную закрыть **новый тестовый заказ** в 1С, подождать настроенную
   задержку, проверить журнал отправок запросов оценки и ответ по кнопке в MAX.
   Проверить также отменённый заказ, повторный callback, неверный MAX user ID
   и срок приёма оценки. Рекомендуется тестировать на отдельном пользователе
   и не отправлять оценки клиентам до проверки работы Webhook.

## Отладка

```bash
docker exec service-car-backend python manage.py check
docker exec service-car-backend python manage.py poll_feedback_requests --observe-only
docker exec service-car-backend python manage.py poll_feedback_requests --send-only
tail -n 80 /var/log/servicecar-max-feedback.log
```

Первые две команды не отправляют сообщения; `--observe-only` **изменяет**
снимки состояний в БД. `--send-only` может отправлять накопленные запросы оценки.

Текущее поведение сервиса зависит от включения в Admin. Секреты нужно держать
в окружении или Docker secrets, а не в файлах репозитория. Существующие
cron-записи `poll_order_notifications` и `poll_news_notifications` сохранять.

MAX API: https://dev.max.ru/docs-api/methods/POST/subscriptions и
https://dev.max.ru/docs-api/use-cases/sending-messages/keyboard.
