# Управление уведомлениями MAX через Django Admin

Два существующих фоновых обработчика (`poll_order_notifications` и
`poll_news_notifications`) теперь получают операционные настройки из **одной**
записи PostgreSQL. Перезапуск контейнера при изменении настроек не требуется.

## Что доступно администратору

В Django Admin: **Уведомления MAX → Настройки уведомлений MAX**.

| Поле | Значение |
| --- | --- |
| Уведомления о статусах заказов | Включить/приостановить опрос 1С и отправку сообщений по заказам |
| Уведомления о новых публикациях | Включить рассылку только новых новостей, опубликованных после включения |
| Адрес сайта для ссылок | Общий HTTPS-адрес без пути: `https://www.cherser-car.site` |

Редактируется только одна запись, создание второй и удаление запрещены.
Нужен сотрудник с правом изменения этих настроек (или суперпользователь).
Непроверенный HTTP-адрес, произвольные пути, query-параметры и логин/пароль
в URL отвергаются. Пустой адрес разрешён: в MAX не будет ссылки на сайт.

## Поведение переключателей

- **Отключение новостей:** публикации на сайте сохраняются, но в MAX-очередь
  не ставятся. При повторном включении фиксируется момент активации:
  накопленные ранее ожидающие доставки пропускаются, а старые неразобранные
  публикации закрываются без отправки. В MAX уходят только новости,
  опубликованные **после последнего включения**. Уже выполняющаяся отправка
  может завершиться при одновременном отключении настройки.
- **Приостановка заказов:** не выполняется опрос статусов и не отправляются
  ожидающие сообщения. После включения опрос возобновится. Если за время паузы
  статус менялся несколько раз, будет виден только последний (обычное
  ограничение polling).
- Каждая cron-команда читает переключатели и URL при новом запуске. Лимит
  отправки фиксирован в коде: до 100 доставок за запуск каждой команды;
  число попыток — 5 с увеличивающейся паузой.
- `--limit N` по-прежнему позволяет вручную переопределить лимит для одного
  запуска (от 1 до 1000). Обе задачи cron продолжают запускаться раз в минуту —
  **интервал cron не управляется Django Admin**.

## Переход с переменных окружения

1. При первом `python manage.py migrate` миграция
   `notifications.0001_initial` создаёт запись настроек.
2. Она один раз переносит значения `MAX_ORDER_NOTIFICATIONS_ENABLED`,
   `MAX_NEWS_NOTIFICATIONS_ENABLED` и адреса сайта из окружения. Если заданы
   оба URL, приоритет у `MAX_ORDER_NOTIFICATIONS_PUBLIC_URL`. Проверить поле
   адреса в админке перед включением рассылки.
3. Если переменных не было, оба переключателя изначально выключены.
4. Дополнительная миграция `notifications.0002_news_activation_cutoff` вводит
   безопасную отсечку для очереди новостей и удаляет из БД прежние поля
   настройки лимита и числа попыток. Она поддерживает переход с уже
   установленной первой миграции.
5. После миграции изменение старых переменных окружения **не влияет** на
   переключатели и ссылку; ими управляет только Django Admin. Устаревшие
   переменные можно удалить из Compose после проверки значения в Admin.

**Оставить в `.env` или Docker secrets:** `MAX_BOT_TOKEN`,
`ONEC_NOTIFICATIONS_SERVICE_KEY` и транспортные параметры интеграции с 1С.
Секреты не сохраняются в модели и не отображаются в Django Admin.
Ключ 1С не следует хранить литералом в отслеживаемом `docker-compose.yml`:
используйте `${ONEC_NOTIFICATIONS_SERVICE_KEY:?required}` и надёжно защищённый
`.env`/секреты сервера. При раскрытии ключа замените его одновременно в 1С
и окружении backend. `ONEC_ALLOW_UNAUTHENTICATED_INTERNAL` не относится к
настройкам MAX: не удаляйте его до настройки учётных данных для внутренних
HTTP-сервисов 1С.

## Развёртывание и проверка

Сначала установить сервисный endpoint 1С из соответствующего PR, затем
обновить backend. Применить миграции и выполнить проверки:

```bash
docker exec service-car-backend python manage.py migrate
docker exec service-car-backend python manage.py check
docker exec service-car-backend python manage.py poll_order_notifications --observe-only
docker exec service-car-backend python manage.py poll_news_notifications --prepare-only
```

Последние две команды **не являются dry-run**: они могут обновить снимки/очереди,
но не отправляют сообщения. Для полноценного теста после настройки прав и
привязок выполнить команды без флагов и убедиться в наличии записей журнала.

Фоновые задачи с `flock` на хосте оставить как раньше; менять расписание не нужно.
Сливать ветку настройки Admin после PR с новостной рассылкой (backMag #76).
