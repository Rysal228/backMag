# Полный отказ от CustomUser приложения

## Что является источником истины
В 1С хранятся пользователи приложения, их профиль, назначенные роли,
активность, MAX ID, пароль и состояния MAX-кодов. Django использует
только `onecId` (UUID ссылки 1С).

Приложение не создаёт и не сохраняет пользователей в PostgreSQL.
`request.user` для API — временный **объект в памяти** NativeUser,
полученный через API 1С после валидации подписи JWT. Полный профиль
запрашивается на каждом аутентифицированном HTTP-запросе.

Для административного сайта Django оставлена **встроенная** модель
`django.contrib.auth.models.User` (`AUTH_USER_MODEL = "auth.User"`).
Это только технические администраторы сайта, **не** учётные записи клиентов.

## JWT и выход
SimpleJWT используется для проверки подписи и срока действия,
но выпуск происходит через `RefreshToken()` без `for_user()`.
Payload содержит `user_id=onecId`, `auth_method`, `active_role`
и для MAX — подтверждённые MAX ID и телефон.

Refresh rotation и logout используют таблицу `users_consumedrefreshtoken`.
Уникальный `jti` допускает только один обмен/выход, второй запрос
с тем же refresh будет отклонён. Для регулярной очистки уже
истёкших JTI: `python manage.py purge_consumed_refresh_tokens`.
Истечение и подпись токена проверяет SimpleJWT. Logout отзывает
refresh-токен, не уже выданные access-токены.

API остался совместимым по публичным полям:
`accessToken`, `refreshToken`, `status:role_selection_required`,
`selectionToken`, профиль `id`. Значение `id` — UUID 1С.

## ВАЖНО: процесс миграции учебного PostgreSQL

**Не запускай эти миграции на действующей БД без плана восстановления.**

Переключение `AUTH_USER_MODEL` с `users.CustomUser` на `auth.User`
меняет Django swappable dependencies. Старые миграции и существующие
таблицы SimpleJWT, `django_admin_log`, доменных FK и пользователей
могут иметь реальные FK на старую таблицу, даже если Python-модели
больше её не используют. Обычное последовательное `migrate`
**не гарантировано**, особенно на старой развернутой базе.

Для учебного проекта рекомендован **полный сброс и создание новой
PostgreSQL базы**, только **после** резервного копирования необходимых
настроек, статусов, расписания, справочников марок/моделей и администратора.
Заполнить эти данные повторно через ранее предусмотренные команды или
fixtures, затем заново создать технического суперпользователя Django
через `python manage.py createsuperuser`.

До первого деплоя новой схемы проверить на **пустой тестовой** БД:
`python manage.py migrate`, `python manage.py check`,
`python manage.py makemigrations --check --dry-run` и полный набор тестов.
Старые миграции могут требовать пересоздания начальной истории миграций
(через проверенную squashed-baseline), если стандартный путь на пустой БД
не проходит. **Не редактируй историю миграций на живой базе.**

## Проверить сквозные сценарии
1. Пользователь создан только в 1С — парольный вход без Django строки.
2. Новый MAX-пользователь, MAX-код, выбор/смена роли.
3. Refresh меняет токен один раз, повторный refresh старым токеном не работает.
4. Logout отзывает соответствующий refresh (проверка владельца).
5. Отзыв роли/деактивация в 1С немедленно блокирует API и WebSocket.
6. Автомобиль, заказ, несколько специалистов, комнаты/сообщения чатов.
7. Django Admin работает отдельно от учётных записей приложения.

Не применять данную ветку, пока схема миграций и тесты не проверены на
пустой PostgreSQL. Объединять после PR #54 и #55.
