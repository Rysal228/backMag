# MAX-уведомления о публикации новостей

## Поведение

- Новость в Django Admin после сохранения вместе с назначенными ролями считается
  опубликованной. Добавление новой новости создаёт `NewsNotificationBatch`,
  редактирование существующей рассылку не повторяет. При выключенной рассылке
  новости по-прежнему публикуются на сайте, но не попадают в MAX-очередь.
  После повторного включения старые публикации не рассылаются.
- Команда `poll_news_notifications` готовит адресную очередь для активных
  пользователей с MAX-привязкой из 1С и отправляет не более 100 сообщений
  за запуск по умолчанию (`--limit` для ручного запуска). Глобальная новость — всем; новости для `user` — владельцам,
  механикам и менеджерам; для `mechanic` — механикам и менеджерам; для `admin`
  — менеджерам. При нескольких ролях используется объединение их прав.
- Доставка повторно проверяет в 1С статус привязки и роли, а также текущую
  видимость новости в Django. Если доступ изменился, отправка пропускается.
  Каждая доставка и результат хранятся в журнале Django Admin. MAX ID не
  сохраняется в PostgreSQL. Предусмотрены 5 попыток доставки,
  задержка между попытками увеличивается (начиная с минуты).
- Сообщение: заголовок, до 700 символов текста и ссылка на конкретную новость
  `/main?news=ID`; если текст отсутствует, остаются заголовок и ссылка.
  Angular открывает и подсвечивает нужную новость, включая старые публикации.
  Изображение из новости **не пересылается** в MAX; оно доступно по ссылке.

## Порядок развёртывания

1. Сначала обновить конфигурацию **1С**, включая метаданные
   `HTTPServices/ServiceCarAPI.xml` и модуль `ServiceCarAPI/Ext/Module.bsl`.
   Выполнить проверку F7, обновить конфигурацию БД и HTTP-публикацию.
   Обновление одного BSL без URL-шаблона не установит метод.
2. Убедиться, что настроен существующий регистр
   `НастройкиСервисаУведомлений` (`main`) и секрет
   `ONEC_NOTIFICATIONS_SERVICE_KEY` в окружении backend. Новый секрет или
   отдельный технический менеджер **не нужны**. На сервере с доступом к 1С:

   ```bash
   python tools/smoke_notification_service.py --base-url http://host.docker.internal:8081/ServiceCar/hs/api
   ```

   Smoke test читает три метода, проверяет отказ без ключа/с неправильным
   ключом, структуру данных; не отправляет MAX-сообщений и не печатает MAX ID.
3. Обновить **backMag** и **frontMag**. Проверить наличие `MAX_BOT_TOKEN` и
   `ONEC_NOTIFICATIONS_SERVICE_KEY` в окружении, выполнить `python manage.py migrate`
   и `python manage.py check`. В Django Admin открыть **Уведомления MAX →
   Настройки уведомлений MAX**, включить уведомления о новостях и указать
   HTTPS-адрес сайта (если нужны ссылки). Переменные `MAX_NEWS_NOTIFICATIONS_ENABLED`
   и `MAX_NEWS_NOTIFICATIONS_PUBLIC_URL` больше не требуются. Полный порядок
   перехода с существующих переменных — в `docs/max-notification-admin.md`.
4. Создать тестовую новость из Django Admin для ограниченной роли; затем
   выполнить вручную:

   ```bash
   docker exec service-car-backend python manage.py poll_news_notifications --prepare-only
   docker exec service-car-backend python manage.py poll_news_notifications --send-only
   ```

   Проверить корректную MAX-доставку и журнал. Повторный запуск не должен
   отправлять новость ещё раз. Начать с ограниченной аудитории, прежде чем
   включать глобальные новости.
5. Добавить отдельную задачу cron (параллельно уже работающей задаче статусов):

   ```cron
   * * * * * /usr/bin/flock -n /run/lock/servicecar-max-news.lock /usr/bin/docker exec service-car-backend python manage.py poll_news_notifications >> /var/log/servicecar-max-news.log 2>&1
   ```

   Запускать на **хосте**, не в каждом Django-процессе. Не изменять и не
   удалять действующую задачу `poll_order_notifications`.

## Надёжность и ограничения

- Публикация фиксируется транзакционно после сохранения ролей в Django Admin;
  сбой 1С или MAX не блокирует работу редактора новостей. Повторный опрос не
  создаёт вторые строки благодаря уникальности пары публикация/пользователь.
- MAX не гарантирует exactly-once при таймауте после фактической доставки:
  при повторе возможно дублирование сообщения. За один запуск отправляется
  не более одного сообщения каждому получателю.
- Если пользователь привяжет MAX уже **после** формирования адресной очереди,
  старая публикация ему не отправляется. При удалении новости очередь удаляется
  вместе с ней. Редактирование текста не меняет уже запланированное сообщение,
  но сужение доступа предотвращает отправку исключённым ролям.
- При выключенной настройке фоновая команда не обращается к 1С/MAX.
  После повторного включения отправляются только публикации, созданные
  после этого момента. Любая старая неотправленная очередь помечается как
  пропущенная, а старые неразобранные публикации закрываются без отправки.
  Повторные попытки допустимы только для публикаций текущего периода включения.
- Серверный endpoint `/notifications/news/recipients` является служебным;
  закрыть от внешнего интернета, не выдавать ключ в браузер. Для отличного от
  доверенного внутреннего `ONEC_BASE_URL` нужен HTTPS.
