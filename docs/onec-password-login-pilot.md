# Пилот парольного входа Django через 1С — выключен по умолчанию

## Что готово

Пользователи уже установили новые пароли через локальную форму 1С
(регистр `ПаролиПользователейПриложения`). Сама запись в 1С
**не переключает Django login**.

Этот PR добавляет к `AuthService.login` **строго ограниченный пилот**
по явному списку номеров. Если номер не указан, поведение
Django-паролей остаётся прежним. MAX, роль в JWT и ID
`CustomUser` не меняются.

Переключение для пользователя происходит только если его телефон
присутствует в переменной окружения:

```dotenv
# По умолчанию ПУСТО (выключено).
ONEC_PASSWORD_LOGIN_PILOT_PHONES=
```

После **проверенного** защищённого HTTP-маршрута можно указать
только номер специально отобранного тестового аккаунта в формате
`7XXXXXXXXXX` (не публиковать реальные телефоны в GitHub).
Несколько номеров разделяются запятой. Звёздочка `*` не является
маской. Никакого иного флага для всеобщего перевода нет.

## Что произойдёт у выбранного пользователя

1. Django передаст введённый пароль клиенту
   `OneCPasswordAuthClient` (только проверенный HTTPS с технической
   Basic-аутентификацией). Клиент **откажется** отправлять пароль
   через старый незащищённый HTTP `:8081`.
2. 1С сообщит `authenticated`, собственный UUID, телефон и роли,
   но **не выдаст хеш пароля**.
3. Django найдёт существующий `CustomUser` по телефону,
   проверит совпадение `onec_id` и ролей с ответом 1С,
   активность пользователя и выдаст прежний формат JWT.
4. Если пароль неверный, идентификатор/роли расходятся или 1С
   недоступна, **не произойдёт резервного входа по старому
   паролю Django**.
5. Смена пароля через Django для номера пилота временно запрещена:
   пока не существует защищённого механизма изменения пароля в 1С.

Остальные пользователи продолжают входить как раньше.
Регистрация новых пользователей и изменение их паролей
остаются в Django — это **не финальная миграция**.

## Прежде чем активировать хоть один номер

- HTTP-сервис `ServiceCarAuth` **ещё не опубликован и его код пока
  не проверен в 1С 8.5.1.1522**. Код отложен в ветке 1С
  `work/servicecar-auth-future`.
- Текущий обработчик 1С рассчитывает на системного пользователя ИБ,
  которого в этой базе нет. Его необходимо адаптировать
  к действительно защищённому HTTP-доступу.
- Нужно обеспечить HTTPS со штатной проверкой имени сертификата,
  реальную техническую аутентификацию на сервере,
  отсутствие обхода через оба алиаса старой публикации на 8081
  и ограничения попыток. Не считать наличие
  `Authorization: Basic` само по себе доказательством проверки.
- Сверить `onec_id`, телефон, статус и роли выбранной учётной записи.
  Только после этого выставлять `ONEC_AUTH_VERIFY_URL`,
  `ONEC_AUTH_API_USER`, `ONEC_AUTH_API_PASSWORD` и
  `ONEC_PASSWORD_LOGIN_PILOT_PHONES` через секретные переменные
  окружения, а не через git.
- Сперва протестировать специально заведённый учебный аккаунт.
  Реальных пользователей и MAX не переключать без отдельной проверки.
- Не публиковать `ServiceCarAuth`, пока нет обеих проверок:
  запрос с валидной Basic по HTTPS проходит, а прямой HTTP на 8081,
  запрос без/с неверной Basic и попытки через оба алиаса отклоняются.

## Локальные тесты (с моками, без сетевого доступа и базы)

```bash
docker compose exec backend python manage.py test \
  users.tests.test_onec_password_login_pilot \
  users.tests.test_onec_password_auth_security -v 2
```

Эти тесты не проверяют развернутый 1С-сервис/Apache и не являются
разрешением включать номер пилота в продакшне.

## Почему не меняем MAX и регистрацию

JWT содержит текущий `CustomUser.id`, от которого зависят FK заказов,
автомобилей и чатов. Установка паролей в 1С не меняет эту связь.
Парольный вход и MAX-аутентификация реализованы независимо.
Одновременное переключение регистрации сейчас создало бы
невосстановимое расхождение при ошибке сетевой интеграции.
