# Вход Django через текущий ServiceCarAPI 1С

Статус: подготовлено в PR #46, **выключено по умолчанию**, работающий
вход Django, JWT, MAX и регистрация не переключены.

## Уже проверено в рабочей 1С (18.10.2026)

Пользователь подтвердил `POST /ServiceCar/hs/api/password/verify`:
- HTTP 200, `authenticated:false` для несуществующего пользователя;
- HTTP 200, `authenticated:true` для существующей пары телефон/пароль;
- при успехе приходят `onecId`, `phone`, `isActive`, `roles`.

Не нужен новый `ServiceCarAuth` или отдельный пользователь ИБ.

## Настройки для одного аккаунта

Прежде чем переключать тестовый аккаунт, проверьте совпадение
`CustomUser.onec_id` с реальным `onecId` из 1С и ролей пользователя.

Настройки окружения **в контейнере Django**, не в GitHub и не в коде:
```dotenv
ONEC_AUTH_VERIFY_URL=http://host.docker.internal:8081/ServiceCar/hs/api/password/verify
ONEC_AUTH_ALLOW_INSECURE_INTERNAL_HTTP=1
ONEC_AUTH_API_USER=
ONEC_AUTH_API_PASSWORD=
ONEC_PASSWORD_LOGIN_ENABLED=0
```

По умолчанию `ONEC_PASSWORD_LOGIN_ENABLED` пусто — **все пользователи
по-прежнему входят через прежнюю проверку Django**.

Значение `1` включает проверку через 1С для всех уже привязанных пользователей (`CustomUser.onec_id`). Значение `0` оставляет существующий вход Django. Номера телефонов в этой переменной указывать не нужно.

### Важный риск выбранного способа подключения

Это осознанное включение **передачи пользовательского пароля по
незашифрованному HTTP между Django и 1С**. Наличие запрета доступа
к порту 8081 с внешнего интерфейса не защищает от наблюдения или
изменения трафика внутри хоста/сети. Рекомендованный безопасный
вариант — HTTPS и авторизованный endpoint, но текущий пилот не
требует их настройки.

Для HTTP в коде разрешён **только точный внутренний URL**
`http://host.docker.internal:8081/ServiceCar/hs/api/password/verify`,
только при явном флаге `ONEC_AUTH_ALLOW_INSECURE_INTERNAL_HTTP=1`;
другие HTTP-адреса запрещены. Basic credentials по HTTP не
передаются. Никакие реальные пароли не вводить в терминальную
историю или переписку.

## Поведение

- У выбранного в пилот аккаунта пароль проверяет 1С. Django
  сверяет `onecId`, телефон, статус и роли со своей временной
  `CustomUser`, затем выдаёт JWT прежнего формата.
- При неверном пароле или недоступности 1С **нет fallback**
  на старый хеш Django.
- Смена пароля через Django для номера пилота временно
  отключена до переноса этой операции в 1С.
- MAX и регистрация остаются без изменений. Django `CustomUser.id`
  остаётся прежним ради FK автомобилей, заказов и чатов.

## Проверки перед объединением и включением

В проекте Django в рабочем окружении запустить:

```bash
python manage.py test users.tests.test_onec_password_auth_security users.tests.test_onec_password_login_pilot -v 2
```

После тестов объединить PR #46 с `master`, обновить код
контейнера и только затем включить один тестовый телефон.
Проверить успешный вход с паролем 1С и отказ с неверным паролем.
Отдельно удостовериться, что обычный Django-аккаунт и MAX
продолжают работать без изменения.

Проблемы с несовпадающим `onecId` или ролями требуют сверки
учётных записей. **Не отключать проверку UUID или ролей ради входа.**
