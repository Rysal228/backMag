# Полное переключение API заказов Django на 1С

Статус: подготовленный PR, **не развернут и не проверен на рабочей 1С**. Действующий Django master до слияния не изменён.

## Ответственность

- **1С `Документы.ЗаказыНаОбслуживание`** — единственный источник заказа, его строк `Работы`, назначений, статусов/оплаты, снимков и бронирования. Django **не пишет** локальные записи заказов.
- **Django** — проверка JWT / активной роли, авторизация внешних маршрутов, серверная проверка допустимости фильтров и проксирование через `OneCOrdersClient`. **Единственная сохраняемая модель заказного раздела Django — `OrderFilterPermission`** (видимость/разрешение фильтров в Angular + Django Admin).
- **Angular** — использует прежние маршруты `/api/v1/orders/`; типы `workTypeId`, `statusId`, `work_status`/другие ID теперь нативные **UUID 1С, а не int PostgreSQL**. Запрещён произвольный `workTypes: [name]`. Заказ `works: []` поддержан. Если фронтенд пока шлёт старые числовые ID/свободный текст, они будут отклонены — это намеренный несовместимый переход, фронтенд надо адаптировать перед выкладкой.

## Что переписано

- `orders.views`: список, карточка, POST, PATCH/PUT, права, 3 команды статусов, каталоги, график, доступность — только через `OneCOrdersClient`.
- `orders.admin`, `orders.models`: только разрешения фильтров. Удалены локальные сериализаторы, FilterSet, бизнес-переходы и сервис расчёта слотов.
- `cars.views`: `hasOrders`, список заказов авто, ограничения редактирования авто и набор доступных специалисту авто читают 1С, без `Order.objects`.
- `chats`: `ChatRoom.order_id` — UUID документа 1С без FK на Django Order; сообщения/вложения по-прежнему PostgreSQL. Права на комнаты по фактическому заказу и назначению специалиста проверяются в 1С. Веб-сокеты также больше не используют локальный `Order`.

## Перед слиянием/развёртыванием: обязательные проверки

1. **Резервная копия PostgreSQL и ИБ 1С.** Если в таблице `orders_order` есть записи, сначала перенести их в 1С, а идентификаторы в связанных чатах сопоставить с UUID документов 1С. Нельзя просто загрузить новые заказы с другими UUID и оставить комнаты со старыми `order_id`.
2. Защитная миграция `orders.0031_orders_state_to_onec` **останавливается, если в прежней таблице Django ещё есть заказы**. Не обходит проверку и не удаляет их. После подтверждённого переноса старые записи можно архивировать/очистить отдельной контролируемой операцией. Физические прежние таблицы миграция **не удаляет** — `SeparateDatabaseAndState` отключает только ORM-описания. `chats.0005_chatroom_native_onec_order_uuid` отвязывает FK и сохраняет старое поле UUID.
3. **В Конфигураторе 1С исправить шаблон** `/orders/{id}/transition-work-statu` → `/orders/{id}/transition-work-status`. Именно последний путь вызывает Django; иначе изменение статуса работ вернёт 404. Выполнить F7 и убедиться в публикации HTTP-сервиса.
4. Испытать все HTTP-вызовы 1С с `actorId`/ `actorRole`: GET/POST/PATCH заказов, статусы, 1С справочники, график и бронирование двух конфликтующих заказов, поиск по машине, `hasOrders`, роли/конфиденциальность.
5. **1С HTTP API должен быть закрыт от прямых внешних запросов** (только доверенный Django, firewall / localhost / сетевой ACL). Сам `actorId` в query параметре **не аутентификация**, открытый сервис позволит его подделать. Для внешней публикации использовать дополнительную подлинную аутентификацию.
6. Прогнать `python manage.py check`, `python manage.py makemigrations --check --dry-run`, `python manage.py migrate --plan`, `python manage.py test` и проверку реальных API. В текущем рабочем окружении GitHub правки выполнены удалённо; **локального запуска этих команд и функциональных тестов не было**. Перед выкаткой миграции могут потребовать правок в зависимости от версии Django/PostgreSQL.
7. Проверить время: Django настроен `Asia/Krasnoyarsk` (+07), парсер дат в HTTP-модуле 1С также ожидает `+07:00`; ИБ/сервер 1С должны интерпретировать даты в той же зоне.
8. Проверить существующую страницу списка заказов Angular. Теперь ID каталогов/статусов — UUID; элементы отображения фильтров по-прежнему задаются через Django Admin. `DELETE /api/v1/orders/{id}/` отдаёт 405 (нет физического удаления документа в 1С).
9. До объединения кода бронирования в общем модуле 1С не редактировать вручную даты заказов через форму Предприятия: сейчас HTTP код отдельно создаёт `ЗанятыеИнтервалы`.

## API пример

Внешний сайт `POST /api/v1/orders/`:
```json
{
  "car": "3bc5c300-d1e0-471e-8f4c-cc1f8610db8c",
  "appointmentAt": "2026-10-23T09:00:00+07:00",
  "works": []
}
```
Django проверяет поля и отправляет JSON на внутренний `POST /ServiceCar/hs/api/orders?actorId=...&actorRole=user`. 1С самостоятельно сверяет контекст с регистром ролей, владельца автомобиля, время и статусы; снимки формируются **в 1С**.

При выборе работы: `"works": [{"workTypeId":"<реальный UUID справочника ВидыРабот>"}]`; свободного `name` в запросе быть не должно.
