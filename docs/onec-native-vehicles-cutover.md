# Переход автомобильных API Django на 1С — ЧЕРНОВИК

## Что изменилось

- `/api/v1/cars/brands/`, `/api/v1/cars/models/`, `/api/v1/cars/` и дочерние действия выполняют обращения к 1С через `OneCCarsClient`.
- Создание/редактирование автомобиля, архивирование, фото (JPEG/PNG/WebP, до 2 МиБ) записываются непосредственно в 1С. Списки 1С возвращают native UUID элементов, без второй таблицы с локальными PK.
- Django продолжает проверять текущую роль, владельца и доступ специалиста через существующие заказы. Связи с заказами остаются в PostgreSQL, сами автомобили в 1С.
- `orders.Order.car_id`, `car_brand_id`, `car_model_id` — нативные UUID 1С; отображаемые исторические характеристики заказа остаются как snapshots.
- `Car`, `CarBrand`, `CarModel`, `CarOwnership` удалены из текущего Django ORM и Django Admin.
- Миграции `orders.0030` и `cars.0008` **не удаляют данные сами**: при наличии старых заказов/автомобилей останавливаются с сообщением о необходимости переноса или явной очистки.

## Перед развёртыванием: обязательные условия

1. Провести импорт, компиляцию и smoke-тесты <1C PR> из отдельной ветки (сначала **в 1С**, не в Django).
2. Закрыть прямой доступ к `ServiceCarAPI` извне; HTTP-операции автомобилей должны быть доступны только сервисной учётной записи с Basic Auth. Задать `ONEC_API_USER` и `ONEC_API_PASSWORD` в секретных настройках Docker Compose, проверить доступ под ними. `ONEC_BASE_URL` / `ONEC_CARS_PATH` должны указывать на правильную публикацию.
3. Проверить совместимость Angular с **UUID вместо прежних числовых PK** марок и моделей (формы, фильтры, маршруты, типы TS и сериализация). Без этой проверки переключать продакшен нельзя.
4. Проверить, что в PostgreSQL больше нет непренесённых заказов и автомобилей; **эти миграции нельзя выполнять на непустой схеме**.
5. Выполнить на отдельном стенде:
   - `python manage.py check`
   - `python manage.py makemigrations --check --dry-run`
   - `python manage.py migrate --plan`
   - `python manage.py migrate --noinput`
   - `python manage.py test cars users.tests.test_native_user_references`
6. Проверить на запущенном сайте вход пользователя, список марок/моделей, создание автомобиля с фотографией, получение по UUID, корректный запрет чужого автомобиля, заказ со ссылкой на автомобиль и фотографии, архивирование/восстановление, переходы заказа.

## Известные ограничения

- **Не тестировалось ни в Django runtime, ни в PostgreSQL, ни на живой 1С** — это не готовый deploy.
- Порядок миграции старой базы с данными не автоматизирован; прежнюю `servicecar_native` с рабочими заказами очищать нельзя без явного решения.
- Фотография хранится в 1С и возвращается как data URI. Проверить CSP/изображения Angular; при большом количестве фотографий целесообразен отдельный медиа-метод.
- Текущая 1С хранит только *текущего* владельца автомобиля; прежняя `CarOwnership` не переносится как история.
- В коде 1С добавлена форма автомобиля, но интерактивная загрузка фото через сам клиент 1С не реализована.

## Почему PR черновой

Автомобили — действующая бизнес-логика и имеют связи с заказами. Мы не можем безопасно автоматически объединить миграции с live PostgreSQL, пока не проверена интеграция и не принято решение о старых заказах.
