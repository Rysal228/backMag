# Замена связей PostgreSQL на UUID из 1С

## Граница этой ветки

Продолжение `refactor/native-onec-uuid-remove-external-id`.
Справочник пользователей, роли, MAX и пароли находятся только в 1С.

В PostgreSQL **не создаются дополнительные UUID пользователей** для
автомобилей, заказов и чатов:
- `Car.owner_id`, `CarOwnership.owner_id` — UUID ссылки 1С;
- `Order.customer_id` — UUID ссылки 1С;
- `OrderMechanic(order, mechanic_id)` — назначение специалиста по UUID 1С;
- `ChatRoom.mechanic_id`, `ChatMessage.sender_id` — UUID ссылки 1С.

Остальные ID сущностей PostgreSQL (автомобиля, заказа, чата) остаются
самостоятельными — они **не** являются идентификаторами пользователя.

Прежние поля HTTP API `mechanics`, `senderId`, `mechanicId`, `ownerName`,
`ownerPhone` не переименовываются. Имя владельца/отправителя извлекается
из 1С с кэшем только в рамках формирования ответа. Заказ хранит
исторический снимок телефона и имени клиента, чтобы поиск по заказам
не зависел от локальной таблицы учётных записей.

## Порядок безопасного развертывания (тестовая база)

**Черновик: не развертывать до тестового прогона миграций.**

1. Убедиться, что в рабочей 1С уже удалён второй идентификатор и
   `onecId` доступен в HTTP API.
2. Сделать резервную копию PostgreSQL.
3. Перед применением миграций удалить учебные автомобили, заказы,
   их работы, слоты, чаты и сообщения. Это **явная отдельная операция**:
   миграции не запускают автоочистку. Конкретные SQL-команды зависят от
   имеющихся связей и должны проверяться на копии БД.
4. Выполнить `python manage.py migrate`. Миграции:
   `cars.0007_native_owner_uuid`,
   `orders.0029_native_user_uuids`,
   `chats.0004_native_chat_participant_uuids`.
5. Проверить `python manage.py makemigrations --check --dry-run`,
   `python manage.py check` и тесты.
6. Проверить вход нового пользователя 1С, добавление авто,
   создание заказа, назначение специалиста, создание комнат чата,
   отправку сообщения HTTP и через WebSocket.

### Что пока НЕ удалено

Модель `CustomUser` и её временные записи с `pk = onecId` в текущей
авторизации Django ещё существуют. После обновления всех зависимостей
авторизации и SimpleJWT их удалим отдельной миграцией. Данные
`users.CustomUser` не являются источником истины; приложение не создаёт
второй идентификатор, их `pk` совпадает с `onecId`.

Не объединять с `master` до согласованного теста миграций и
существующего черновика PR #54.
