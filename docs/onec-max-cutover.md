# Перенос авторизации MAX в 1С (поэтапное внедрение)

## Граница ответственности

- **Angular не меняется:** остаются /api/v1/users/auth/max/, /max/code/request/,
  /max/code/verify/, /select-role/, /switch-role/, /password/ и текущие ответы.
- **Django:** проверяет HMAC и срок жизни MAX initData и подтверждения
  контакта; нормализует телефон; генерирует 6-значный случайный код и
  отправляет сообщение через MAX Bot API; временно хранит UUID/JWT/FK
  пользователя для заказов/автомобилей/чатов.
- **1С:** источник истины по привязке MAX ID к телефону и native пользователю,
  созданию пользователя с пустым паролем, ролям, действительности/однократности
  кодов, времени выдачи, 60-секундному интервалу и 5 попыткам. Регистр
  `КодыАвторизацииMAX` хранит **хеш**, дату, попытки, признак использования
  и ID запроса, а не открытый код. Старую таблицу Django MaxAuthCode пока не
  удалять: она не используется новыми обработчиками, но понадобится на этапе
  безопасной очистки миграций.
- Проверка существующего MAX ID без повторного доступа к контакту остается.
  Если MAX-пользователь есть только в старой базе Django, его подтвержденная
  связка MAX ID/телефон переносится в 1С при следующем входе.
- Назначенные роли берутся из 1С и синхронизируются во временный Django-миррор
  исключительно после проверки идентичности.

## Требуемая конфигурация 1С

В репозитории 1c (ветка `feature/max-auth-onec`) добавлены:

- HTTP-сервис `ServiceCarAuth` (/ServiceCar/hs/auth), **четыре POST-шаблона**:
  `/max/resolve`, `/max/code/issue`, `/max/code/verify`,
  `/max/code/cancel`;
- обработчики в его модуле, допускающие только авторизованного технического
  пользователя информационной базы **servicecar-auth**;
- регистр сведений `КодыАвторизацииMAX` с измерением Пользователь (ссылка
  на `ПользователиПриложения`) и ресурсом Состояние (строка до 1024);
- обновлённые XML метаданных, Configuration.xml и ConfigDumpInfo.xml.

**Важно:** `1Cv8.cf` в GitHub не пересобран. Не устанавливать старый .cf поверх
текущей базы. Загрузить исходники в тестовую конфигурацию, проверить синтаксис
модуля и корректность метаданных в Конфигураторе 1С 8.5, обновить конфигурацию
базы данных, создать/настроить техническую учетную запись с минимальными правами,
затем перепубликовать HTTP-службу. Без проверки в конфигураторе это изменение
нельзя считать прошедшим тестирование на платформе 1С.

## Настройки Django (только в secrets/.env, не коммитить)

```text
ONEC_MAX_BASE_URL=https://<hostname>/ServiceCar/hs/auth
ONEC_MAX_API_USER=servicecar-auth
ONEC_MAX_API_PASSWORD=<technical-password>
```

Требуются **реальный HTTPS с проверкой сертификата** и HTTP Basic
для этого пользователя. Никакой HTTP/редирект или безымянный
интеграционный endpoint не допускается, включая внутренний host.docker.internal.
Разрешить доступ к сервису только с Django-сервера и закрыть его от интернета.
Не логировать тела запросов (там есть разовый код/номер).
MAX_BOT_TOKEN остается только на Django, в 1С не копируется.

Без этих трех настроек MAX в Django возвращает 503 и **не** пытается
авторизовать по старой Django-базе. Пока 1С не обновлена, нельзя
выкатывать новый Django код.

## Поведение и защита от рассинхронизации

1. Django проверяет initData, а при передаче контакта — его подпись.
   В 1С отправляются только **проверенные** MAX ID и телефон.
2. Сначала запрашивается привязка по MAX ID. Если она существует, телефон
   снова запрашивать не нужно (кроме forceContact). При новом MAX ID
   требуется подтверждённый телефон либо ранее связанный в Django MAX ID.
3. 1С атомарно проверяет конфликт MAX ID, телефона и externalId, сохраняет
   привязку и отдаёт onecId + externalId + роли. Новый пользователь в 1С
   создаётся без пароля с ролью user.
4. Django сверяет ID, телефон, MAX ID, isActive, onecId, externalId;
   создаёт/обновляет только временный локальный UUID/JWT/roles-миррор.
   Несовпадение — 409/502, JWT не выдаётся.
5. Код: Django получает криптостойкую случайную строку, 1С сохраняет хеш,
   Django отправляет код через Bot API; при ошибке доставки Django пытается
   отменить только конкретный requestId. 1С отклоняет уже использованный,
   просроченный и многократно введённый код.
6. На refresh, смене роли, выборе роли и установке **первого** пароля
   MAX-сессия снова сопоставляется с текущей привязкой в 1С. Ошибки 1С
   не превращаются в удачную авторизацию.
7. Для новых MAX-only аккаунтов `hasPassword=false` в 1С; создание пароля
   по подтвержденной MAX-сессии и смена существующего пароля продолжат
   работать по прежним маршрутам.

Сервисные endpoints /max/* — **не публичный API**: их нельзя открывать без
серверной авторизации; фронтенд никогда не отправляет в них проверенные
identity-assertions напрямую.

## Проверка перед выпуском

В контейнере Django (после публикации тестовой 1С):

```bash
python manage.py test users.tests.test_onec_max -v 2
python manage.py test users.tests.test_onec_password_auth_security users.tests.test_onec_registration users.tests.test_onec_profile_gateway -v 2
```

Тесты в GitHub в этой ветке не исполнялись (нет доступа к живой 1С).
Полезны следующие **ручные** кейсы на тестовой связке:

1. Первый вход MAX с контактом → новая запись в 1С без пароля,
   user-роль, связанный native ID, JWT и GET profile.
2. Повторный вход MAX без контакта → прежние ID, без дубликатов.
3. Привязка MAX к существующей парольной записи 1С с тем же externalId;
   попытка привязать чужой MAX ID или телефон → 409 без изменения записи.
4. Пользователь только в старом Django MAX → безопасная миграция связки в 1С
   при авторизации без запроса повторного контакта.
5. Код 000123, неправильные цифры, повтор, 5 попыток, TTL 5 минут,
   ограничение переотправки 60 секунд, ошибка Bot API → отмена.
6. Роли user/mechanic/admin, выбор роли и refresh, удалённая смена роли,
   блокировка аккаунта в 1С → старый MAX JWT не продлевается.
7. Отказ 1С, отсутствие TLS/Basic, чужой externalId, неверная подпись
   initData или телефона → отказ без JWT.
8. MAX-only → задать первый пароль; затем сменить по текущему
   (логика создания/смены пароля не менялась).

## Важные ограничения

- Два разных хранилища (1С + Django) **не имеют общей транзакции**.
  Возможен частично завершённый шаг при сбое сети. До переключения
  продакшена проверить идемпотентные повторные запросы и наличие всех
  старых MAX-пользователей в 1С; сохранять резервные копии обеих баз.
- Временный Django-миррор/UUID и JWT пока остаются для зависимых систем.
  После миграции автомобилей/заказов можно отдельно убрать эти зависимости.
- Для веб-атак необходим лимит запросов на публичных HTTP маршрутах
  (IP и номер телефона) на reverse proxy. Лимит 60 секунд в 1С ограничивает
  повторную выдачу одному аккаунту, но не защищает весь периметр.
- Изменения **не были проверены в работающей платформе 1С**.
  Сначала test/staging и review, затем публикация.
