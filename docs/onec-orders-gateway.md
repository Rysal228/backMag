# Заготовка шлюза заказов 1С (без включения на production)

## Статус
Этот PR **только добавляет** `integrations.services.onec_orders.OneCOrdersClient` и изолированные тесты. `orders.views`, Django ORM заказов, расписание, чаты и текущие URL по-прежнему работают через PostgreSQL. В 1С ещё нет готовых HTTP-операций заказов. Поэтому **этот PR не является завершённым переносом**.

Модель объектов и подробный контракт для **ручного создания через Конфигуратор**: [`Rysal228/1c/docs/manual-orders-cutover.md`](https://github.com/Rysal228/1c/blob/feature/manual-orders-onec-contract/docs/manual-orders-cutover.md) (ветка `feature/manual-orders-onec-contract`).

## Конфигурация
`ONEC_BASE_URL` (по умолчанию `http://host.docker.internal:8081`), `ONEC_ORDERS_PATH` (по умолчанию `/ServiceCar/hs/api`). Шлюз заказов использует те же правила Basic Auth, что и действующие пользователи/автомобили: у штатного внутреннего адреса обе `ONEC_API_USER`/`ONEC_API_PASSWORD` необязательны; у других адресов обе обязательны. Пара частично заданных значений запрещена. HTTP-сервис 1С нельзя открывать напрямую в интернет.

## Уточнённые требования от 21.10.2026

- Документ 1С — **`Документы.ЗаказыНаОбслуживание`** (это точное имя актуального main), вместо изначально предложенного `ЗаказыНаРемонт`.
- **Работы необязательны.** `works` может отсутствовать или быть пустым массивом, заказ остаётся корректным с ценой 0.
- **Только справочные виды работ.** Каждая непустая строка передаёт `workTypeId` (нативный UUID `Справочник.ВидыРабот`); никаких свободных `name` или `workTypes` с названиями, даже если старый Django это разрешал. Название возвращает 1С из справочника.
- **Свободные смены статусов.** В `transition-status` и `transition-work-status` менеджер (`admin`) может установить любой существующий статус своего справочника, без матрицы разрешённых пар, автоматических переходов связанного статуса или требования `paid` для `execution`. Контроль роли, действительности статуса и доступа к заказу остаётся. Для оплаты сохраняется отдельная команда.
- Старые Django `OrderSerializer`, `OrderWorkflowService` и связанные формы Angular пока не изменены: это осознанно до подтверждения работающего API 1С; **нельзя выдавать черновой PR за готовый cutover**.

## Контракт
- `actor_id` — только из проверенного Django JWT. `actor_role` — только из `request.active_role`; библиотека запрещает другие значения и не позволяет фильтрами переписать `actorId` / `actorRole`.
- Оба параметра передаются в **query** (`actorId`, `actorRole`) для всех методов. При реальном cutover 1С **должна перепроверять** пользователя, его активность и право роли через собственные данные, а не просто принимать значение query.
- Методы: `work_types`, `order_statuses`, `work_statuses`, `payment_statuses`, `schedule`, `availability`, `list_orders`, `get`, `create`, `patch`, `permissions`, `transition_status`, `transition_work_status`, `set_payment_status`, `filter_permissions`, `car_orders`, `car_has_orders`.
- Все ID заказов, авто, работ и статусов после cutover — **нативные UUID 1С**. Сохранять внешние URL `/api/v1/orders/`, `/api/v1/cars/{id}/orders/`, но для фронта надо обновить ожидаемые типы ID.
- HTTP-ошибки с валидным JSON `{code,message}` для 400/403/404/409 передаются наружу; другие ошибки обобщаются. Нет ложного «успеха» при таймаутах и недоступности 1С.

## Зависимости для следующего PR cutover

1. Создать вручную 1С-справочники, документ, табличные части, регистры и HTTP-обработчики; запустить настоящие тесты доступности/записи/блокировок/состояний с тестовой базой 1С.
2. Переписать Order serializers/views/filter/pagination, сохранив поведение Angular, и убрать ORM-бизнес-правила из Django только после эквивалентных проверок в 1С.
3. Обновить `cars/views.py`: `hasOrders`, список машин механика, `/cars/{id}/orders/` должны использовать один источник 1С, а не таблицы Django.
4. Обновить `chats/models.py` и миграции: `ChatRoom.order` сейчас FK к `orders.Order`, заменить на `order_id` с UUID 1С и адаптировать `chats.views`/`chats.permissions`/`chats.serializers`. Чаты и файлы при этом остаются в Django, если пользователь не менял цель.
5. Текущие `orders.Order` и связанные таблицы удалить только после исключения всех импортов и связей. Без удаления данных и с проверкой состояния PostgreSQL. Django Admin заказов должен стать read-only/прокси или быть удалён, иначе админка запишет не в тот источник.
6. Подтвердить клиентский формат даты и часовой пояс, стабильную нумерацию, вместимость расписания и возможность удаления/архивирования; убрать принудительные зависимости статусов и при этом явно определить политику освобождения записанного времени.
7. Провести smoke и параллельные тесты: создание двух заказов на один слот, проверки чужого клиента, выбор **любого** статуса менеджером, запрет переключения чужой роли, оплата, заказ без работ, запрет произвольной работы, назначение механика, все роли, список заказов машины и чаты.

## Локальный запуск изолированных контрактных тестов

```sh
cd autoservice
python manage.py test orders.tests.test_onec_orders_gateway
```

Тесты мокируют 1С; они не доказывают работоспособность BSL и публикации. Прямое переключение на неподготовленную 1С недопустимо.
