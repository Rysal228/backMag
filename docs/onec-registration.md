# Регистрация через 1С — замена хранения паролей Django

Схема после совместного развёртывания 1С и Django:

1. Фронтенд не меняется: POST /api/v1/users/auth/register/.
2. Django создаёт `CustomUser` с **непригодным для входа** паролем
   (аргумент `password=None`), сохраняет временную роль `user`.
   Эта запись необходима текущим JWT, заказам, автомобилям, чатам.
3. Django сначала проверяет готовность 1С по существующему GET
   /ServiceCar/hs/api/user/profile и требует
   `passwordRegistration: true`. Если обновление 1С ещё не
   применено, новая регистрация не создаст пользователя без пароля.
4. Django делает POST в существующий `/ServiceCar/hs/api/user`:
   `phone`, `externalId` = UUID `CustomUser.id`, ФИО,
   `birthday`, `roles:["user"]`, `password`.
5. 1С сохраняет элемент справочника, роль и солёный хеш пароля
   в одной транзакции, возвращает `user.onecId`.
6. Django сверяет UUID, телефон, externalId, активность и роль,
   записывает `CustomUser.onec_id` и выдаёт прежний JWT.

Пользовательские пароли **не сохраняются как Django-хеши**;
MAX и суперадминистраторы Django остаются на своих механизмах.
GET /api/v1/users/auth/password/ теперь читает `hasPassword` у 1С,
а не вызывает `has_usable_password()`. Изменение пароля на сайте
по-прежнему временно отключено.

## Порядок развертывания (важно)

**Сначала 1С:** обновить в Конфигураторе модуль ServiceCarAPI
из ветки `Rysal228/1c:feat/onec-password-registration`,
проверить синтаксис и обновить конфигурацию БД 1С.
Никаких новых URL-шаблонов не требуется. Признак
`passwordRegistration:true` должен появиться в GET /user/profile,
а статус `hasPassword` — в ответе существующего GET пользователя.

**Затем Django:** после объединения PR, на сервере
`git pull` и `docker compose up -d --build backend`.
В контейнере:

```bash
python manage.py test users.tests.test_onec_registration \
  users.tests.test_onec_password_auth_security \
  users.tests.test_onec_password_login_pilot -v 2
```

И только после этого через сайт зарегистрировать *нового тестового*
пользователя с отдельным номером телефона, проверить успешный
повторный вход с паролем 1С и отказ при неверном пароле.
Не помещать реальные пароли в истории команд/логи.

Для известного внутреннего ServiceCarAPI дополнительных
флагов подключения Django не требуется. Если определены
`ONEC_BASE_URL`/`ONEC_USERS_PATH`, они должны указывать на
действующие адреса. Для кастомных/внешних URL клиент по-прежнему
требует учётные данные. Пароль между Django и 1С сейчас
передаётся без шифрования через внутренний HTTP.

## Не удаляем старые данные слепо

Из живого пути регистрации и входа Django-хеши убраны.
Но Django `CustomUser`, UUID и роли пока нужны для JWT/связей;
удаление модели сломает действующие данные. Django
`CustomUserManager` остаётся для создания системных
пользователей и MAX-аккаунтов с непригодным паролем.
Самостоятельное изменение пароля через 1С — следующий этап.

**Важно:** транзакции PostgreSQL и 1С независимы. При обрыве
связи после фиксации 1С, но до сохранения `onec_id` в Django
возможна неполная регистрация. При HTTP 409 нужно сверить
`phone` и `externalId` в 1С перед повторной попыткой —
не удалять пользователей и не менять UUID автоматически.
