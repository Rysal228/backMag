# Финальный этап отказа от CustomUser

Этот набор изменений кладётся **поверх** PR #54 и #55. Основной пользователь
существует исключительно в 1С. HTTP API, Angular и JWT используют
`onecId` (UUID ссылки справочника). `users.auth.identity.OneCUser` —
не ORM-модель, а неизменяемый объект текущего запроса.

## Что остаётся в PostgreSQL

Автомобили, заказы, чаты, их UUID-ссылки на пользователей 1С, служебные
справочники и настройки. Отдельно хранится только таблица
`users.RevokedRefreshToken` (JTI, expiration) для выхода из аккаунта
и одноразовой ротации refresh-токенов. Дубли пользователей, ролей, паролей,
MAX-кодов в Django отсутствуют.

Django Admin использует **стандартную** модель `auth.User` и отдельные
технические логины, которые **не являются** пользователями приложения 1С.
Стандартные endpoint'ы `/api/token/` и `/api/token/refresh/` отключены.
Публичный API продолжает работать через `/api/v1/users/auth/`.

## Обязательный порядок развёртывания

1. Подтвердить, что новая 1С из `main` уже использует только `onecId`.
2. Сохранить резервную копию обеих БД.
3. Использовать **чистую тестовую БД PostgreSQL или полностью пересоздать
   схему**, поскольку меняется `AUTH_USER_MODEL` с `users.CustomUser`
   на `auth.User`. Удаление отдельных строк в старой схеме не решает
   вопрос исторических Django ForeignKey и таблицы `django_admin_log`.
   **Никакой DROP/очистки не запускается кодом миграций автоматически.**
4. На чистой БД выполнить `python manage.py migrate` (включая
   `cars.0007`, `orders.0029`, `chats.0004`, `users.0010`).
   Затем `python manage.py check` и
   `python manage.py makemigrations --check --dry-run`.
5. Для отдельной технической админки создать логин командой
   `python manage.py createsuperuser` — это **не** учётная запись 1С.
6. При необходимости отдельно восстановить служебные статусы/переходы,
   расписание, марки автомобилей и иные справочники PostgreSQL.
7. Проверить регистрацию, MAX, пароль, установку первого пароля,
   выбор роли, refresh/logout, отзыв роли в 1С, автомобили, заказы,
   специалистов, REST и WebSocket-чаты.
8. Проверить, что старые JWT с UUID Django не проходят проверку.
   Пользователям сайта потребуется повторно войти.

## Описание JWT

`accessToken` и `refreshToken` сохраняют существующие названия
и поля `user_id`, `auth_method`, `active_role`;
MAX добавляет `messenger_user_id` и `max_verified_phone`.
Каждый защищённый REST-запрос заново валидирует пользователя и роль в 1С.

`refreshToken` ротируется при каждом обновлении: старый JTI фиксируется
в PostgreSQL. Повторное использование старого JTI отклоняется. Logout
записывает JTI в тот же реестр; текущий access-токен действует максимум
до своего срока истечения (стандартные 60 минут), если роль/активность
не изменены в 1С. Техническое обслуживание:
`python manage.py cleanup_expired_refresh_tokens`.

## Важные ограничения

- Это изменения исходников; проверка `manage.py migrate`, системные
  проверки, CI, интеграционные тесты 1С здесь ещё не запускались.
- Старые тесты, основанные на двух UUID и `CustomUser`, должны быть
  адаптированы к новой модели. Не объединять PR до проверки.
- Общий список всех пользователей в 1С пока не предоставлен. Маршрут
  `GET /api/v1/users/?role=mechanic` сохранён, прочие списки явно
  возвращают ошибку вместо поиска в удалённой Django-таблице.
- Django Admin не может редактировать пользователей приложения: ими
  администрируют из формы 1С.
