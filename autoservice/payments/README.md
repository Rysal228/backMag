# ServiceCar — подготовка эквайринга (Россия)

В этой ветке **НЕТ** реального приёма денег: нет ключей, обращения к эквайрингу,
публичного webhook, редиректов на оплату или изменения `СтатусОплаты` в 1С.
Это намеренно. Не включать на production оплату посредством подмены ответа API.

## Готовые интерфейсы (только авторизованные JWT)

- `GET /api/v1/payments/capabilities/` — `enabled: false`, провайдер не выбран.
- `GET /api/v1/payments/orders/<uuid>/preview/` — только роль **user**;
  берёт сумму и статус из 1С от лица клиента; `canPay: false`.
- `POST /api/v1/payments/orders/<uuid>/start/` — только **user**, всегда
  возвращает HTTP 503 `payments_not_configured`, **денег не списывает**.

PostgreSQL хранит **пока пустые** технические таблицы `PaymentAttempt`
(заказ/клиент UUID 1С, сумма счёта, идемпотентность, идентификатор провайдера,
состояние) и `PaymentEvent` (дедупликация проверенных уведомлений). Django Admin
предоставляет только чтение. Реальные статусы заказа и оплаты остаются в 1С.

## Перед включением ЮKassa или другого провайдера

1. Получить договор и ключи у платёжного провайдера, настроить тестовую среду.
   Выбрать способ выдачи чеков по 54-ФЗ.
2. **Сначала исправить безопасность production:** запретить прямой доступ к
   внутреннему HTTP-сервису 1С; проверить серверную аутентификацию Django→1С;
   убрать `DEBUG=True` на production, сменить опубликованные пароли БД и
   вынести секреты из кода в окружение/секретное хранилище.
3. Зафиксировать счёт/сумму в 1С и запретить незаметную правку оплаченного счёта;
   не доверять сумме или клиентскому ID из браузера.
4. Реализовать провайдер через интерфейс `PaymentProvider` с серверными
   ключами, уникальным idempotency key, проверкой владельца заказа и возврата.
5. Реализовать защищённый webhook: не доверять телу или redirect URL,
   независимо получать платёж у провайдера по API и сверять account/shop,
   order ID, сумму/валюту, финальный статус; сохранять событие однократно.
6. Сохранять подтверждение в транзакционном журнале и доставлять событие в 1С
   через надёжный повторяемый механизм; повторная доставка не меняет баланс
   и не создаёт дубль. Результат списания денег **не равен** успеху синхронизации.
7. Разработать отмены, частичные возвраты, reconciliation, ограничение запросов,
   тесты дублей webhook, сетевых отказов и повторных оплат. Проверять фронтенд
   как недоверенную сторону; реальные операции разрешает только сервер.

## Локальная проверка

```bash
cd autoservice
python manage.py check
python manage.py makemigrations --check --dry-run
python manage.py test payments --keepdb
python manage.py migrate
```

Публичные UI кнопки оплаты оставлять неактивными до реализации следующего этапа.
